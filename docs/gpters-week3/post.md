# 제목

기능은 다 만들었는데, 진짜 돌아갈까? — Claude Code + bkit으로 PDCA 10바퀴 돌려 블로그 자동화 도구를 검증한 3주차 기록

## 소개

### 시도하고자 했던 것

2주차에는 강의 1·2주차 원칙을 제 블로그 자동화 도구 **19auto-blog**에 옮겼습니다. 수집 → 글감 보드 → 재료·규칙 → 단계형 초안 → 이미지 세트 → 발행 확인, 이렇게 6단계입니다. 감사하게도 그 발표로 베스트 발표자에 뽑혔습니다.

발표가 끝나고 든 생각은 하나였습니다.

**"기능은 다 만들었는데, 이거 진짜 제대로 돌아가나?"**

그래서 3주차(10/16~10/22)에는 기능을 더 늘리지 않고, 남은 숙제 세 가지를 풀었습니다. 10/19 발표회에서 중간 결과를 발표했고, 이 글은 그 뒤 사흘 동안 한 작업까지 합친 최종본입니다.

1. **검증** — 만들기는 다 만들었는데, 실제로 돌려 보고 확인한 건 많지 않았습니다.
2. **디자인** — 글이 어느 단계까지 왔는지 한눈에 안 보였고, 휴대폰에서 확인해 본 적도 없었습니다.
3. **이미지 품질** — 그림이 글 내용과 따로 놀았습니다.

(콘텐츠&지식 과정인데 하다 보니 개발 과정이 됐습니다 ㅎㅎ)

### 왜?

- **검증이 늘 '나중에'로 밀렸습니다.** 2주차까지는 Claude Code(Sonnet 5.5), Gemini 3.8 Flash, Grok 4.7을 번갈아 썼습니다. 기능은 빨리 늘었지만, 도구를 바꿀 때마다 맥락이 끊겼습니다.
- **그림이 글을 설명하지 못했습니다.** "비밀번호 검사 기능을 끄려면?" 소제목에 다이얼과 상자가 들어가는 식이었습니다. 운영 글 3편을 AI로 채점해 보니 5점 만점에 3.6, 2.3, 3.2점이었습니다.
- **실제로 쓰는 사람이 생겼습니다.** 스터디 동기들이 써 볼 수 있게 사이트를 로그인 없이 열었습니다. 남이 쓰는 도구라면 "돌아가는 것 같다"로는 부족했습니다.

## 진행 방법

### 사용한 도구

- **Claude Code (Opus 5.5)** — 여러 도구를 오가던 것을 이것 하나로 정리했습니다. 계획부터 구현·테스트·배포까지 씁니다.
- **bkit** (Claude Code 플러그인) — 계획 → 설계 → 구현 → 검수 → 개선 → 보고 → 보관을 하나의 루프로 돌립니다. 이번 주의 핵심 도구입니다.
- **Claude API (Haiku 5.5)** — 도구 안에서 글쓰기, 이미지 장면 계획, 이미지 채점(그림을 직접 보고 점수 매기기)
- **Ideogram 3.0 API** — 블로그 이미지 생성
- **Vercel + Neon Postgres + GitHub Actions** — 배포, 이미지 저장(Blob), 매시간 자동 작성
- **gbrain** (개인 지식 저장소, MCP) — 결정할 때마다 기록해 두어, 대화를 지우고 새로 시작해도 맥락이 이어지게 했습니다.

### 1단계: 디자인 — 시안 3개 중 고르기

대시보드 시안을 세 개 만들어 비교했습니다.

- A: 흰 바탕 + 인디고, 위쪽에 5칸 진행 줄
- B: 종이색 + 명조 제목, 원형 단계 표시
- C: 어두운 바탕 + 5열 칸반 보드

**C를 골랐습니다.** 글 하나가 지금 어느 단계(수집 → 글감 → 재료·규칙 → 초안 → 발행 대기)에 있는지 한눈에 보이기 때문입니다. 그 뒤 화면 색을 종이·흰·어두운 3가지로 늘리고(기본은 종이), 신문 1면 같은 제목과 Ctrl/⌘K 명령창을 붙였습니다. 명령창은 휴대폰에서 키보드에 가리지 않게 따로 고쳤습니다.

### 2단계: bkit으로 "검수가 빠지지 않는" 루프 만들기

bkit을 한 줄로 말하면 **AI가 만든 코드를, AI가 쓴 설계서와 대조해서 검사하는 도구**입니다.

- 계획서와 설계서를 먼저 쓰고, 구현이 끝나면 **설계와 코드가 몇 % 일치하는지** 점수를 매깁니다.
- 일치율과 별도로 비용·보안·동시성 문제를 분석합니다.
- 단계마다 사람에게 묻습니다. "이 범위 맞아요?", "설계안 A·B·C 중 무엇으로 할까요?"

저는 자동화 단계를 L1(단계마다 확인)로 두고, 명령 한 줄로 시작한 다음에는 거의 "**다음 진행**"만 입력했습니다.

```
/bkit:control level 1                  단계마다 확인받기

/bkit:pdca plan    <기능 이름>          계획서
/bkit:pdca design  <기능 이름>          설계서 (설계안 3개 중 선택)
/bkit:pdca do      <기능 이름>          구현
/bkit:pdca analyze <기능 이름>          설계와 코드 일치율 검수
/bkit:pdca report  <기능 이름>          완료 보고서 + 커밋 + PR
/bkit:pdca archive <기능 이름>          문서 보관
```

제가 정한 규칙은 세 가지뿐입니다.

- 각 단계가 끝나면 **"다음 진행"**
- 검수에서 고칠 범위를 물으면 보통 **"모두 수정"**
- 커밋·PR은 보고서 단계에서, **머지는 "PR N 머지해줘"라고 말할 때만**

### 3단계: 다음 할 일을 프롬프트 파일 하나로 넘기기

대화가 길어지면 `/clear`로 비우고 새로 시작합니다. 그래도 맥락이 끊기지 않도록, **다음 할 일과 붙여 넣을 프롬프트를 파일 하나(`docs/bkit-next-prompts.md`)에 모아 두었습니다.** 새 대화에서는 이 파일의 프롬프트만 붙여 넣으면 됩니다.

실제로 쓴 프롬프트 전문입니다. 먼저 이미지 관련성 개선 한 바퀴 전체입니다.

```
/bkit:pdca plan image-relevance
블로그 이미지가 글 내용과 어긋난다. 소제목마다 독자가 떠올릴 실제 대상(제품·화면·장소·행동)이 보이게 바꾸고 싶다.
범위: docs/image-relevance-prompts.md의 진단 원인 5가지(상징물 강제, 실제 대상 지시 없음, 예시 문장 섞임, 생성 후 관련성 검사 없음, Ideogram 설정).
완료 기준: 운영 글 #42~#44를 다시 계획했을 때 모든 장면에 글 속 고유 대상이 들어가고, 관련성 점수(1~5) 평균 4 이상.
글 1편당 추가 비용 상한과 Vercel 300초 제한 안에서 끝나는지도 계획서에 숫자로 적어줘.

/bkit:pdca design image-relevance
설계안 3개를 비용·실행 시간·확인 방법 기준으로 표로 비교해줘.

/bkit:pdca do image-relevance
구현 후 검증 4단계를 돌리고, 운영 글 #44로 이미지 계획 전후 비교표를 만들어줘.
실제 Ideogram 생성은 1편만 하고 결과 이미지를 보여줘.

/bkit:pdca analyze image-relevance
gap-detector와 code-analyzer를 둘 다 돌려서 설계 일치율, 비용·시간 초과 위험을 같이 보여줘.

/bkit:pdca report image-relevance
끝나면 커밋하고 PR까지 만들어줘. 머지는 내가 말할 때.
```

활동 기록의 AI 길이 경고 표시를 브라우저로 확인하고 결과를 표로 정리해줘.

### 4단계: 이미지가 글과 맞게 — 네 바퀴

**원인** (bkit 계획 단계에서 정리했습니다)

1. 글 속 실제 대상 없이 상징물만 그렸습니다.
2. 프롬프트 예시에 넣은 색(청록·주황)이 모든 글에 번졌습니다.
3. 그림이 글과 맞는지 확인하는 장치가 아예 없었습니다.

**1바퀴 — 대상을 먼저 정하고, AI가 채점**

1. 소제목 본문에 실제로 나오는 **대상(anchor) 하나**를 먼저 정합니다. 예: "카드 서랍장"
2. 글 종류에 맞춰 화풍을 고릅니다. 뉴스는 사진풍, 사용법은 손으로 작업하는 사진풍, 개념 설명은 일러스트입니다.
3. 그림을 만든 뒤 **AI가 그 그림을 직접 보고** 1~5점과 이유를 남깁니다.
4. 3점 미만이면 한 번 다시 만듭니다. 비용이 새지 않게 글당 2장까지만 합니다.
5. 화면의 "이미지 세트 다시 만들기"는 글마다 하루 3번까지로 막았습니다.

채점 프롬프트 전문입니다. `${...}` 자리에 소제목·뜻·대상이 들어갑니다.

```
블로그 이미지가 글 내용과 맞는지 채점하세요.

[소제목] ${input.h2}
[전달할 뜻] ${input.point}
[보여야 할 대상] ${input.anchor || '(없음 — 소제목 뜻으로 판단)'}

[채점 기준]
5: 보여야 할 대상이 분명히 보이고 소제목 뜻과 맞음
4: 대상이 보이고 뜻이 대체로 맞음
3: 주제는 관련 있으나 대상이 흐리거나 일부만 보임
2: 일반적인 그림이나 상징물뿐, 대상이 없음
1: 내용과 무관하거나, 손·얼굴 왜곡 또는 읽히는 글자가 크게 보임

[감점하지 않는 것]
- 화면·문서의 글자와 숫자가 흐리거나 읽히지 않는 것 (일부러 흐리게 그립니다). 단, 보여야 할 대상이 화면 속 내용 자체라면 흐려서 알아볼 수 없을 때 3점 이하입니다.
- 색·재질이 대상 묘사와 다른 것 (화풍이 정합니다)
화면 밖(종이·노트·간판·물건)에 알아볼 수 있는 글자·숫자·손글씨가 있으면 작아도 3점 이하입니다.
이 두 가지 말고는 위 기준대로 채점합니다. 손·얼굴 왜곡이나 크게 읽히는 글자는 여전히 1점입니다.

아래 형식의 JSON만 <score> 태그 안에 출력하세요. 다른 설명은 쓰지 않습니다. reason은 무엇이 보이고 무엇이 빠졌는지 한국어 한 문장(60자 이내)입니다.
<score>{"score": 4, "reason": "..."}</score>
```

**3바퀴 (발표 후) — 숫자·글자가 원래 있는 사물은 고르지 않기**

운영 장면 162장의 점수와 이유를 모아 보니, 3점 17장 중 11장이 **달력·계기판·온도계 같은 글자 사물**이거나 **키보드 치는 손**이었습니다. "숫자 없는 달력"이라고 써도 숫자가 그려졌습니다. 그래서 금지하는 말을 붙이는 대신 **그 사물 자체를 고르지 않게** 했습니다. 장면 규칙 3줄을 넣고, 그래도 고르면 코드가 찾아서 그 장면만 다시 계획합니다.

**4바퀴 (발표 후) — 빈 종이 장면 줄이기**

채점 평균은 4.22로 높았는데, 눈으로 보면 이상했습니다. 소제목 장면의 32%가 빈 노트·체크리스트·폴더였고, 눈으로 점검한 16장 중 11장은 뜻이 안 보였습니다. 그래서 "지금 무엇을 하면 되나요?" 같은 할 일 소제목은 **첫 번째 할 일을 실제 대상에 하는 장면**으로, 빈 종이는 **글당 1장**까지로 바꿨습니다.

3·4바퀴에서 장면 규칙(이미지 장면을 계획하는 AI 프롬프트)에 추가한 줄의 전문입니다.

```
- 질문형·추상 소제목(확인 방법·영향·위험·정도·차이·아직 모르는 것)은 소제목 단어가 아니라 그 소제목 아래 첫 문단의 답이 가리키는 구체 대상이나 결과로 anchor를 고릅니다. 예: "버전이 영향을 받나요?"의 답이 "공유 호스팅 서버가 영향을 받습니다"면 서버 랙이 anchor입니다. "확인한다·입력한다·읽는다"를 키보드 치는 손이나 화면을 보는 사람으로 그리지 않습니다.
- 할 일 소제목("지금 무엇을 하면 되나요", "무엇을 준비/확인해야 하나요", "어떻게 해야 하나요")은 첫 번째 할 일을 그 실제 대상에 하는 장면으로 그립니다. 예: "서버라면 무엇부터 점검하나요"의 답이 "PHP 버전을 올립니다"면 서버 랙 앞에서 케이블을 다시 꽂는 손입니다. 빈 노트·체크리스트·클립보드·폴더나 책상 위 소품(머그·휴대폰)만 있는 장면은 고르지 않습니다.
- 빈 종이류(노트·종이·체크리스트·폴더·카드·봉투)는 한 글에서 1장까지, 종이 자체가 주제(규칙 문서·계약 서류·보고서·공지·편지)일 때만 씁니다. 운영 글 장면의 3분의 1이 빈 종이여서 글마다 비슷해 보였습니다.
- 숫자·글자가 원래 있는 사물(달력·시계·스톱워치·타이머·계기판·온도계·자·저울, 카드·명찰·양식·증서·라벨·태그·티켓·영수증·간판·포스터·번호판)은 anchor로도 소품으로도 쓰지 않습니다. "숫자 없는 달력"처럼 없애는 말을 붙여도 숫자가 그려집니다(운영 #69·#77). 시간·정도·신원 같은 뜻은 다른 사물이나 행동으로 보여줍니다.
- 상태 하나(닫힘·비어 있음·똑같은 두 개)에 뜻을 맡기지 않습니다. 이미지 모델은 상태를 자주 놓칩니다(닫힌 상자가 열려서, 똑같은 폴더가 다르게 그려졌다). prompt와 must에는 보여야 할 것만 쓰고 no text·no numbers·no label 같은 말은 쓰지 않습니다. 빼야 할 것은 avoid에 씁니다.
```

AI가 규칙을 어겼을 때 찾아내는 코드 일부입니다. 찾으면 그 장면만 한 번 다시 계획합니다.

```ts
// 할 일 소제목("지금 무엇을 하면 되나요", "무엇부터 점검하나요", "어떻게 확인하나요")
const ACTION = /(하면|해야|해 두면|봐야)\s*(되나요|하나요|할까요|좋을까요|좋나요)|무엇부터|어떻게\s*(\S+\s+)?(설치|적용|대비|준비|대응|확인|점검)|준비해야|대비하/;

export function isActionHeading(h2: string) {
  return ACTION.test(h2);
}

// 빈 종이류 anchor. 한국어 anchor가 문서를 가리키면 종이가 주제라 세지 않는다.
export function paperWord(scene: ImageScene) {
  if (DOCUMENT.test((scene.anchor ?? '').split(' / ')[0])) return null;
  const match = anchorEnglish(scene).split(BESIDE)[0].match(PAPER);
  return match ? match[1].toLowerCase() : null;
}
```

### 5단계: 검증 장치 만들기 (발표 후)

- **휴대폰 화면 점검 스니펫** — "휴대폰에서 오른쪽이 잘린다"는 의심이 있었는데, 운영 사이트와 실제 휴대폰에서 재현되지 않았습니다. 그래서 CSS를 덧대지 않고, 개발자도구 콘솔에 붙여 넣으면 약 60초 만에 7개 페이지 × 390·430px, 14개 조합의 넘침을 표로 알려 주는 스니펫을 남겼습니다. 결과는 14개 모두 넘침 0이었습니다.
- **운영 DB를 건드리지 않는 로컬 실행** — `npm run start:local` 한 줄이면 로컬 DB(SQLite)를 강제로 쓰고 자동 실행(크론)을 끈 뒤, 운영 공개 API(읽기 전용)에서 글·재료·규칙·프로필 사본을 5초 만에 채워 띄웁니다. 운영 글 60개가 전부 같은 값으로 들어옵니다.
- **AI 응답 길이 경고** — AI가 답하기 전에 '생각하는' 토큰까지 길이 제한에 들어가서, 이미지 계획이 4번에 1번꼴로 잘렸습니다. 이제 모든 AI 응답이 사용량을 재고, 제한의 80%를 넘으면 활동 기록에 "AI 길이 경고"를 남깁니다.
- **AI 호출을 한 길로 모으기** — AI를 직접 부르는 곳 5곳을 2곳으로 줄였습니다. 다음에 호출 방식을 바꿀 때 고칠 곳이 하나입니다.

## 결과와 배운 점

### 결과 (3주차, 10/16~10/22)

- PR 20개(#14~#33), bkit PDCA **10바퀴**
- 운영 글 3편(이미지 19장)의 관련성 평균 **3.05 → 3.89**. 가장 낮던 #43은 **2.3 → 4.0**
- 같은 3개 글을 새 규칙으로 다시 그린 19장: 숫자가 읽히는 그림 **2장 → 0장**, 3점 이하 **6장 → 3장**
- 할 일 소제목 등 바뀐 장면 14장: 눈으로 봐서 뜻이 분명한 그림 **2장 → 9장**
- 자동 테스트 **27개 → 162개**. 바퀴마다 타입체크·린트·빌드·테스트 4단계를 통과했습니다.
- 설계 일치율: 검수에서 나온 문제를 고친 뒤 바퀴마다 99~100%
- 비용: 글 한 편에 약 $0.21(Claude + Ideogram), 채점·다시 만들기로 최대 약 $0.14 추가. 효과 검증용 이미지는 3바퀴 $1.14, 4바퀴 $0.84를 썼습니다.

### 배운 점 & 나만의 꿀팁

1. **검증은 의지가 아니라 도구가 챙겨야 합니다.** 루프 안에 검수가 들어 있으니 바쁠 때도 확인이 빠지지 않았습니다. 그리고 매 바퀴 검수에서 제가 생각 못 한 문제가 나왔습니다. 예를 들어 이미지 다시 만들기 버튼은 무제한으로 누를 수 있었습니다(한 번에 약 35센트). 그래서 글마다 하루 3번으로 막았습니다.
2. **AI 점수는 흔들립니다.** 같은 그림도 1점씩 오르내립니다. 채점 기준만 바꿨는데 평균이 3.71에서 3.93으로 오르기도 했습니다. 그래서 기준을 바꿀 땐 그 효과부터 따로 재고, 두 번 이상 채점하고, 0.2점 이하 차이는 개선으로 세지 않습니다.
3. **마지막은 사람 눈입니다.** 채점기는 노트에 엉터리 숫자가 그려진 그림에 5점을, 뜻이 안 보이는 빈 종이 장면에 4~5점을 줬습니다. 눈 점검을 "분명·약함·결함" 세 칸으로 정해 숫자로 셌더니, 점수에 안 보이던 문제가 보였습니다.
4. **꿀팁: 고치기 전에 운영 데이터부터 모으세요.** 장면 162장의 점수와 이유를 표로 모으니 원인이 두 종류로 좁혀졌습니다. 규칙 위반을 찾는 코드도 운영 장면에 먼저 돌려서, 엉뚱하게 걸리는 경우(글자 없는 출입증 리더기, 웹 화면을 뜻하는 page)를 이미지를 만들기 전에 잡았습니다.
5. **꿀팁: 바뀐 것만 다시 만들어 비교하세요.** 이미지 세트 전체를 다시 만들면 안 바꾼 장면까지 흔들립니다. 4바퀴는 바뀐 소제목 14장만 그려서 $0.84로 효과를 확인했습니다.
6. **꿀팁: 다음 할 일은 프롬프트 파일로 넘기세요.** `/clear` 뒤에도 파일 하나로 이어집니다. 보고서의 "남은 항목"이 다음 프롬프트가 됩니다.

### 시행착오

- **로컬 테스트인 줄 알았는데 운영 DB였습니다.** `.env`의 DB 주소가 운영 Postgres라서, 10/16부터 3일 동안 로컬 서버가 운영 DB에 붙어 있었습니다. 그 사이 로컬에서 만든 그림 6장은 PC에만 저장되고 주소만 운영 글(#37)에 들어가서, 운영에서 그림이 깨졌습니다. 2주차 글에도 비슷한 실수를 적었는데, "조심하자"로는 막히지 않았습니다. 그래서 실행 명령 자체를 나누고(`npm run start:local`), PC에 남은 원본을 저장소(Blob)에 올려 주소만 바꿨습니다. 이미지를 새로 만들지 않아서 비용은 0이었습니다.
- **AI의 '생각' 토큰도 길이 제한에 들어갑니다.** 이미지 계획이 4번에 1번 잘렸습니다(제한 8,000 → 16,000 토큰). 채점 답도 300토큰에서 잘려 JSON이 깨졌습니다(→ 1,024 토큰).
- **"없애라"고 써도 그려집니다.** "숫자 없는 달력"이라고 써도 숫자가 나왔습니다. 금지하는 말을 붙이는 대신, 그 사물을 고르지 않게 했습니다.
- **하나를 막으면 다음으로 무난한 소품으로 옮겨 갑니다.** 빈 종이를 막자 배송 상자가 새 단골이 될 조짐이 보였습니다.
- **목표를 고친 범위보다 크게 잡았습니다.** 2바퀴는 3점 장면 2장만 고쳤는데 글 평균 4.2를 목표로 잡아서, 채점 흔들림 안에서 "미달"이 났습니다. 목표는 "바꾼 장면이 2회 채점 모두 4점 이상"처럼 고친 범위에 맞춰야 판정이 정확합니다.

### 도움이 필요한 부분

- **이미지 속 엉터리 글자**: Ideogram이 기기·상자 표면에 상표 같은 글자를 넣습니다. 제외어(negative prompt)를 넣어도 남습니다. 비슷한 문제를 풀어 보신 분의 경험을 듣고 싶습니다.

- **검색량 데이터**: 글감 보드의 검색량은 아직 "확인 필요"로만 둡니다. 네이버 검색광고 API·데이터랩, 구글 트렌드를 연동해 보신 분의 조언이 필요합니다.
- **OSMU 유튜브**: 원본 하나로 여러 채널에 내는 기능 중 유튜브 쪽이 아직 제대로 안 나옵니다. API에서 받아오는 부분이 문제인지 보고 있습니다.
